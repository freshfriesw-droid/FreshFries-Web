# Fresh Fries LUXE — نظام خدمة العملاء والتوصيل
**الحالة: نسخة تطوير واختبار — غير معتمدة للتشغيل الرسمي.**

## النسخة الحالية
- واجهة الويب: `v38.38.0`، عربية ومتجاوبة مع الجوال.
- قاعدة البيانات: Supabase `v38.23` (نسخة المخطط المسجلة في `ff48_release_manifest`).
- الخادم: PostgreSQL، صلاحيات RLS، دوال RPC مخولة، وخدمة `ff61-employees` لطلبات التوظيف.
- البيئة: استضافة GitHub Pages وعنوان `delivery.freshfriesz.com`.
- API Gateway: `https://api.freshfriesz.com`، مفتاح نشر public فقط في المتصفح.

## تحديث التشغيل v38.38.0 — 21 نوفمبر 2026
- تم السماح بإلغاء الطلب بعد قبوله من الموصل وحتى قبل تسجيل تسليمه للعميل، مع تنبيه أحمر للكاشير وإقرار مستقل بإلغاء الفاتورة إن وجدت.
- تظهر هوية الموصل المتوقع بجوار مراجعة الطلب، وهي توقع لحظي لا يضمن الإسناد النهائي.
- القوائم الجانبية تُفتح عند الطلب فقط؛ تبرز حالة الكاشير باللون الأحمر وإطار واضح لكل طلب.
- المدير لديه معاينة وتصفير تشغيلي انتقائي أو شامل مع نسخة احتياطية وتأكيدين؛ **لا تشمل العملية حسابات الدخول والفروع والأصناف وسجل التدقيق الرئيسي**.
- التقييمات ذات خمس نجوم وتعليق اختياري، وتظلمات الموصلين، مع منع تعطل مرحلة التسليم إذا فشل حفظ التقييم.
- يستطيع المدير استعراض الواجهات والتدخل في مراحل التوصيل ضمن تسلسلها الصحيح مع سبب إلزامي وسجل تدقيق، دون انتحال هوية الموصل.
- أزيلت إعادة تحميل الصفحة القسرية عند تبديل الحساب؛ يلزم فحص سرعة الدخول من أجهزة المطعم وشبكته قبل اعتماد النتيجة.

## تحديث محلّل الطلبات
- محلّل واحد للطلب الجديد والإضافات بعد الإسناد، مع معاينة تفصيلية قبل الإرسال وملاحظات أصناف مستقلة ومرادفات.
- قبول الاسم الثنائي على الأقل في طلبات الانضمام، وإظهار شعار المطعم لأيقونات PWA.

## المكونات
الطلبات حسب الفرع، استقبال العملاء، إسناد الموصلين، دورة الكاشير، نقطة التجميع الاختيارية، الحجوزات، العروض والمنيو، حسابات الموظفين والصلاحيات، طلب الانضمام وموافقة الإدارة، رسائل الموظفين، التقارير التشغيلية، شاشة متابعة العميل بالهاتف المتحقق منه.

### بوابة الانضمام للموظفين
يقدم الشخص بياناته بغير إنشاء حساب فعال؛ الإدارة تراجع الطلب والصلاحيات والفرع وتختار كلمة مرور، ثم ينشأ المستخدم من الخادم وليس من المتصفح.
- الهاتف يؤكد بإجراء إداري يدوي؛ البريد لا يعامل بأنه متحقق إلا بعد التحقق الحقيقي من ملكيته.
- لا تُعطَ صلاحية الإدارة من نموذج التقديم.
- تُحفظ سجلات ومراجعات القرارات في قاعدة البيانات.

### بوابة العملاء
يظهر زر «متابعة طلباتي» في شاشة الدخول. تطلب الواجهة رمز OTP من Supabase Auth، ولا يمكن للدالة `ff28_customer` كشف الطلبات إلا لرقم هاتف يمني موثق في حساب العميل، مع منع الموظفين من دخول بوابة العملاء. يتطلب عمل إرسال SMS تفعيل مزود رسائل في إعدادات Supabase Auth وتجربة واقعية قبل اعتماد هذه الميزة.

## PWA وتخزين البيانات
يوجد `manifest.webmanifest` و`sw.js` و`offline.html` وأيقونات PNG بالحجمين 192 و512. لا تُخزن بيانات الطلبات أو الجلسات خارج الاتصال؛ تحميل صفحات النظام من الشبكة فقط. **وصول إشعارات Web Push في الخلفية غير معتمد** حتى ينفذ ويربط خادم الإرسال ومفاتيح VAPID واختبارات جهاز حقيقية.

## الفحص الآلي
تعمل GitHub Actions على كل دفعة لمراجعة JS وPWA والمداخل الأساسية: `.github/workflows/luxe-static-qa.yml` مع `scripts/luxe-static-ci.mjs`.
هذه الاختبارات **ليست بديلًا** عن فحص شامل للدوال والصلاحيات، ولا عن اختبارات الأجهزة والتزامن وإرسال SMS وWeb Push والأحمال. لا تعلن جاهزية الإنتاج حتى اجتياز ذلك.

## إجراءات قبل الاعتماد
1. تفعيل مزود SMS وفحص OTP بحساب عميل مستقل في بيئة آمنة، والتأكد من عدم ظهور طلبات عملاء آخرين.
2. إكمال خادم Web Push وربط الاشتراك والتحقق من إرسال واستقبال إشعارات حقيقية.
3. اختبار الموافقات وتسجيل دخول الموظفين الفعليين بعد تأكيد البريد.
4. اختبار الكاشير والموصلين والتجميع والتزامن بين جهازين لكل فرع، وحالات التعارض والرفض والإلغاء.
5. إجراء اختبار تحميل وتصحيح Advisor في بيئة اختبار معزولة، ثم اعتماد خطة نسخ احتياطي واسترجاع.
6. التأكد من ظهور الموقع وملف PWA من شبكة المطعم في صنعاء؛ قد تتأثر الاستضافة بتوجيه DNS أو الحجب المحلي.
7. مراجعة مؤشرات Supabase Security وPerformance Advisors، خصوصًا صلاحيات `SECURITY DEFINER` وإعداد حماية كلمات المرور المسربة.

لا يُنفذ أي حذف أو تصفير تشغيلي ضمن عمليات الفحص الآلي.
